- **Status:** Design brief prepared; implementation waits for BOOT-01 acceptance
- **Depends on:** BOOT-01, SPEC-03
- **Requirement coverage:** US-01/03; FR-09/10/12/15; NFR-03/07/08

- **Owner:** Luna Max implementation agent; root reviews and integrates

## Objective and scope

Build only the early UI-00 slice against the existing application setup and reviewed fixtures: (1) desktop map with a linked incident feed, (2) mobile list-first discovery with a map switch, (3) event detail with claim evidence and update history, and (4) read-only moderator evidence review. Treat the mobile and desktop layouts as responsive forms of the same public discovery experience. Keep the interface inside the accepted UX/API contracts; do not change APIs, add dependencies or data sources, create synthetic examples beyond reviewed fixtures, or expand into preferences, briefings, notifications, authentication, or moderation actions.

Before implementation, present this visual direction and the four wireframes for root review in the task handoff. The design below is the approved starting proposal; adjust implementation details only where the existing setup requires it and report the reason.

## Visual direction and tokens

**Direction: Jakarta field atlas.** A quiet, legible civic bulletin built around the map/feed relationship, source trails, and time labels. Use a paper-like neutral canvas, strong dark text, and one river-teal accent. Keep the map and evidence legible under time pressure; avoid dashboard chrome, gradients, glass, generic chatbot treatment, and repeated oversized cards. Data and geometry carry the visual character; decoration does not.

| Token | Value | Use |
| --- | --- | --- |
| Hujan Pagi | `#F4F7F5` | Page and quiet panel background |
| Tinta Kota | `#18323A` | Main text and high-contrast structure |
| Kali Teal | `#087B75` | Links, selected controls, supported map selection |
| Beton | `#D5DEDB` | Rules, inactive borders and map grid |
| Kuning Perhatian | `#E7B448` | Caution marker paired with a shape/icon and text label |
| Merah Tanda | `#A7433B` | Urgent or disputed marker paired with a shape/icon and text label |

The selected text/background pairs were checked in WSL: Tinta Kota on Hujan Pagi is 12.51:1, Kali Teal on Hujan Pagi is 4.75:1, Merah Tanda on Hujan Pagi is 5.55:1, and Tinta Kota on Kuning Perhatian is 7.08:1. Do not place Tinta Kota text on a Merah Tanda fill; use white text on that fill or use Merah Tanda as text/line color on Hujan Pagi. Statuses still need words/icons/patterns as well as color.

- **Typography:** Use Plus Jakarta Sans if already available locally; otherwise use the existing system sans-serif stack without adding a font dependency or remote font request. Use the same family for headings and body. Headings are compact and sentence case; body text is at least 16 px; supporting text is at least 14 px. Use tabular numerals for time and count comparisons. Keep paragraphs short and left-aligned.
- **Spacing and layout:** Use a 4 px base rhythm, with 8/12/16/24/32 px steps. Align the main content to a clear left edge. On desktop, use a stable feed/map split with the feed slightly under half-width and the map taking the remainder; preserve a useful feed when the map is hidden or unavailable. On mobile, make the list the default, expose an explicit `Daftar` / `Peta` switch, and keep filters and map controls reachable without gestures.
- **Status expression:** Lifecycle, freshness, evidence, and relevance remain separate labelled fields. Pair colors with words, icons, or line patterns. Make event/observation, publication, and system-fetch times separately identifiable. Only render fixture-backed points, official boundaries, or documented segments; do not expand a point to a radius.

## Interface and safety boundaries

- Use the server-selected dataset mode and record-level `dataset_kind`; show the persistent demo banner for historical/synthetic fixtures. Never derive “live” from a browser flag or fixture timestamp.
- Bind each public claim to only its own displayed source attribution. Keep event/observation time distinct from source publication time and system fetch time; retain date/range/unknown precision from the contract.
- Show lifecycle, freshness, evidence status, and relevance as independent labels. Do not label model confidence as verification.
- If a source or map is unavailable, identify the unavailable component and last known successful time where the fixture/API provides it; preserve list access. Empty results state that this does not mean the area is safe.
- Keep source-backed map geometry exact. Historical crime reports stay as attributed historical reports, never current danger zones. Items without geometry remain discoverable with an explanation.
- Moderator screens are read-only. Do not add approve, publish, edit, correct, merge, retract, source-approval, or account-management controls or calls before MOD-01.
- Render realistic Bahasa Indonesia UI copy, but take all event names, dates, locations, evidence, source labels, and updates from the reviewed fixture. Do not invent live examples.

## Accessibility and visual QA

- Use semantic headings, buttons, links and labels; every icon-only control has an accessible name. Keep visible `:focus-visible` states and keyboard operation, including a list alternative for all map features.
- Test at 200% zoom and at narrow mobile width. Honor `prefers-reduced-motion`; avoid nonessential animation. Error states give a next step; loading, empty, source-unavailable, map-unavailable and demo states are distinct.
- After implementation, run the assigned WSL Ubuntu-26.04 checks, launch the UI against the local Worker, and capture at least one desktop and one mobile screenshot. Review the screenshots against this brief and refine before handoff.
- Apply the Anthropic frontend-design checklist during planning/critique and the Vercel Web Interface Guidelines during final code review. Report concise file/line findings and any fixes in the handoff.
