# AUTH-01 — Google accounts, roles and onboarding

15 October 2026. Assigned at main396263a following explicit user requests for onboarding/authentication/roles, Google login with public browsing account-free, and parity in Android Flutter plus responsive web. Mobile admin/dashboard remains out of scope. This supersedes the no-account/no-login portions of ADR-006/028 only; publication, source approval, correction and review mutations remain disabled. Preserve MOD-01, UI-00 and original mobile IDs; this is the identity/onboarding slice, not completion of their write scope.

## Accepted direction and boundaries

Optional Google identity only; no passwords or email service. New verified Google subjects become `user`, never first-user admin and never by email-domain/client input. Server roles: `user`, `moderator`, `admin`. Google identity keyed by issuer+subject, not email. Visitors keep all public map/report/history/local interests. User account adds profile/session and a three-step onboarding (reading status, optional local interests, privacy). Store only onboarding version/time, not precise location or inferred audience. Account role may be displayed but is never user-selectable at signup/onboarding. Admin web may list a bounded account page and assign roles/disable another account with reason/version; invalidate target sessions atomically, audit minimally and deny self modification. Revalidate actor account in the mutation transaction. Initial admin requires an explicit local/operator provisioning command; no public bootstrap endpoint or automatic promotion.

Web Google authorization-code flow uses maintained OpenID library, state, PKCE S256, nonce, exact configured callback and safe hash return target. Opaque random session tokens are hashed at rest and HttpOnly/host-only; production `__Host-waspada_session; Secure; SameSite=Strict; Path=/`, OAuth-attempt cookie SameSite=Lax for Google callback. Explicit loopback-only development cookies may omit Secure and use different names. Idle30min / absolute8h, revocation/active/dataset/current-role check on each protected request. Same-origin exact Origin + synchronizer CSRF for every cookie-authenticated write; login start is same-origin POST with JSON and a custom request header. No CORS credential sharing, token browser storage, provider errors/tokens/PII in logs. Session replies no-store.

Native Android uses official Google Sign-In SDK; sends its ID token only over HTTPS to a distinct native exchange, server verifies signature/issuer/audience/expiry/verified email via maintained JOSE. Server returns a separate opaque mobile session to OS secure storage, never shared preferences. Native bearer sessions may access own session/onboarding/logout only; reject them from admin APIs even if account has a privileged role. Browser cookie credentials never accepted by native exchange; Origin-bearing browser calls may not mint native reusable tokens. No native OAuth client secret, admin UI, embedded WebView auth, device location request or background source/model work. Real Google configuration/device verification remains a final external gate, not fabricated local proof.

No public data contract changes or source/model calls. Target Workers/Neon Free using existing Postgres executor; no hosted changes or paid features. Auth disabled/misconfigured is fail-closed for account features, and public app stays usable. Local tests use injected verified identity providers and disposable isolated PGlite; any demo identity selector is loopback-only, explicit opt-in and visibly synthetic, with no production auth bypass.

## Frozen HTTP contract account-v1

Types are in `apps/worker/src/contracts/accounts.ts`. All account responses no-store. Same public error shape `{code,message,request_id}`; never raw provider errors. Closed input objects, bounded JSON, no user-selected dataset/role except admin's authorized role operation.

- `GET /api/v1/auth/session`: anonymous or authenticated SessionEnvelope; disabled runtime is anonymous with login flags false. Authenticated response contains CSRF for web, null for native; no reusable token.
- `POST /api/v1/auth/google/start`: web same-origin JSON `{return_to}` where return_to is an allowed local hash (`#akun`, `#mulai`, `#admin`, `#tinjau-bukti`); header `X-Waspada-Request: 1`; response `{authorization_url}` plus short-lived attempt cookie. No role choice. Handler validates trusted app origin, not request Host for configuration.
- `GET /api/v1/auth/google/callback`: one-time browser-bound state/PKCE/nonce, establish rotated session,303 to configured origin and safe local hash; new accounts go to `#mulai`. Failure redirects to `#masuk` with generic indication only, never code/token/error details.
- `POST /api/v1/auth/google/native`: native-only JSON `{id_token}`, no browser Origin/cookie auth; verified provider identity yields `{session_token,session:SessionEnvelope}`. Use bearer token on following native account requests; body max16KiB, safe failure, rate limiting. No admin capability for native sessions.
- `POST /api/v1/auth/logout`: current session, CSRF+Origin for web / bearer for native; revoke exact session, clear web cookie,204.
- `POST /api/v1/account/onboarding`: current session, web CSRF+Origin or native bearer; exact `{version:1}`, idempotent completion; response SessionEnvelope. No privacy-checkbox coercion, interest upload or role input.
- `GET /api/v1/account/users?limit=20&after=<id>`: active completed web admin only; max50, stable bounded ID keyset; `{data:AccountUser[],next_cursor:string|null}`. No identity subjects/tokens/private session metadata returned.
- `PATCH /api/v1/account/users/{id}`: active completed web admin only; `{role,active,expected_version,reason}`; same-origin CSRF; atomic actor/target checks, revoke target sessions, minimal audit; return AccountUser;409 on stale/self modification. No user deletion/source/publication authority.

Rate-limit login/exchange using durable short-lived counters and a trusted client-key input; never trust arbitrary forwarded headers locally. Expired attempt/session/counter cleanup is bounded. Moderator/admin UI routes are role-gated on web; neither new auth nor role alone enables L4 mutation routes. Existing illustrative evidence/demo component remains read-only.
