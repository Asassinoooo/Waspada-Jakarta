# ADR-020 — Public event-history disclosure

- **Status:** Accepted for implementation
- **Date:** 26 September 2026
- **Owners:** Team 12

## Context

The public `HistoryEntry` contract requires a `change_type`, `changed_at`, and a concise `summary`. Stored event versions establish their exact identity and publication time, but their content alone does not establish whether a change should be described as a correction, impact change, or retraction. Model-generated labels and summaries could misstate the record. The accepted API-PUBLIC-HISTORY-READER-CORE returns only untrusted internal version records and deliberately does not create these public claims.

## Decision

- Every public history entry must have a moderator-reviewed disclosure record bound to its exact `(dataset_kind, event_id, event_version)`.
- The moderator explicitly selects a `change_type` already allowed by the public contract and writes the public summary. Neither value is inferred by an LLM, computed from a text diff, or copied from an unreviewed event summary.
- `changed_at` is the exact version's stored `published_at`; the separate review timestamp records when the disclosure metadata was reviewed. These times must not be conflated.
- Only approved disclosure metadata for published versions of a currently public live event may be projected. A missing, revoked, stale, or mismatched review cannot be treated as approval. The future Layer 4 projector must not silently return a partial history page when a candidate version lacks its required reviewed metadata; it must fail closed or report history as unavailable.
- Withdrawn versions are not public history entries. If the latest event version is withdrawn, the event and its entire history remain absent from the public views. Retraction details are not exposed.
- Moderator authentication, authorization, review writes, and audit of real decisions belong to MOD-01. Until those controls exist, tests may use authored fictional review rows only. The public DTO remains unchanged unless a later decision explicitly revises it.

## Consequences

The database stores append-only, version-bound disclosure decisions and exposes only the latest approved row through a least-privilege view. The public history projector joins every candidate version to its exact reviewed metadata and constructs the existing `HistoryEntry` allowlist. The later exact-live history reader/runtime composes those approved records only when the event remains current-public; withdrawn events and all their history stay hidden. This decision itself does not enable a Worker database binding or hosted deployment. Source rights, current-public checks, and the normal Layer 4 publication gate continue to apply.

## Affected requirements

FR-10/12/13; NFR-01/07.

## Amendment (HOSTED-02, 16 Nov 2026): agent-path review summaries are deterministic templates

- Each published version writes one approved row to `public_event_history_review_decisions` (migration 050 grants the publication writer insert on it). The row's `summary` is a fixed Bahasa Indonesia template, never model output:
  - agent auto-publication: `Diterbitkan otomatis dari {n} sumber`
  - moderator publication: `Diterbitkan oleh moderator`
  - moderator correction: the moderator's own note, trimmed and truncated to 500 characters, or `Dikoreksi oleh moderator` when the note is blank.
- `change_type` is `published` for a new publication and `corrected` for a correction. Withdrawals and no-material-change decisions write no review row.
- The stored event record is the domain schema 2.0 Event with exactly the 23 keys the public readers check. `publication_mode` and waivers stay on the publication decision row and are not copied into the record.
- Known gap: the agent path does not yet persist support evidence references, claim origins or place ids for a published claim. The stored claims therefore carry empty `support` and `origin_ids`, and the event scope carries no place id. The public Layer 4 projection rejects such a version and fails closed until those inputs exist. No geometry is mapped from the model's approximate coordinates, because no source supports them.

## Amendment (HOSTED-10, 16 and 17 Nov 2026): one point for an approximate coordinate, otherwise the whole map view

Owner decisions: points on the map are convenient and loose (16 Nov), and there is no Jakarta-centre fallback point (17 Nov). The rule is in `apps/worker/src/layers/l4-application-integration/public-point.ts`.

- **One point when there is a coordinate.** An event with a usable approximate coordinate has one Point with role `approximate_place`, `precision_m` null and `precision_basis` unknown. The point is the agent's `approximateCoordinates`, labelled `model_approximate`, when it is finite and inside the sanity box (lat -6.4 to -5.0, lon 106.6 to 107.1). The box is a plausibility check, not a boundary. A source coordinate would come first when a source gives one (none does today). No radius, polygon or line is ever written.
- **No usable coordinate: whole view, no point.** Such an event gets no geometry row. Its decision records `geometry_status` `whole_view` and `geometry_source` null. The DTO carries `location_display` `whole_view`. The map fits the Jakarta extent, shows no pin, and never reuses another event's point or the Jakarta centre as a pin. The Jakarta-centre fallback point and its label `Perkiraan pusat Jakarta, lokasi belum diketahui` are removed.
- **Group notice with no location.** It is listed with `location_display` `whole_view`. The decision records `geometry_status` `not_required_group_notice`.
- **Coordinate-bearing events are pending.** The publication role cannot write geometry rows. Its grants are unchanged: no INSERT on `geometries`, `geometry_evidence` or `event_claim_geometries`. A coordinate-bearing event therefore records `geometry_status` `pending_geometry_writer` and `geometry_source` `model_approximate`, and writes no geometry row. Open decision: a separate narrow geometry-writer role, or defer. This amendment does not choose.
- **Label rule.** A non-group event needs a place id or a location label. The proposal carries no place id, so the label is the test. A non-group event with no label is `INVALID_EVENT` at publish, with or without a coordinate. The 17 Nov wording could be read as narrowing this to "no label and no coordinate". It is kept as the wider rule, pending owner confirmation.
- **Publication never refuses for a point.** The publication is no longer refused because a point cannot be written. A coordinate-bearing event is published with `pending_geometry_writer`, and an event with no usable coordinate with `whole_view`.
- **Evidence.** A publication fills each claim's `support` from the persisted evidence of the proposal's own grounding context, only when the proposal came from one report revision.
- **DTO field.** `location_display` (`point` or `whole_view`) is an optional, additive field on `EventView` in `apps/worker/src/contracts/public-api.ts`. The web map must handle `whole_view` (fit the Jakarta extent, no pin). That is outside this change.
- **Still hidden on the DB path.** No origin writer exists, so `origin_ids` stay empty and the strict projector still rejects these events as `INVALID_EVENT`. The projector's target rule (a geometry or place) is unchanged, so an agent event with no place id and no geometry row has no public target there. The list skips such events and the page does not fail. Public attribution also needs an approved `public_attribution_review_decisions` row, which no writer creates. All of these remain gated.
- **Unchanged.** The ADR-061 automatic gate still reports `location_missing` for an event with no label and no coordinate, so a location-less group notice waits for a moderator. The moderator publish path has no location check, so it lists the notice. The reject and moderation rules are unchanged.

This amendment supersedes the sentence in the HOSTED-02 known-gap note that says no geometry is mapped from the model's approximate coordinates.

## Amendment (HOSTED-14, 17 Nov 2026): no invented location, and source_text for source-stated coordinates

Owner decision: the agent can never make up a coordinate or a region. A location is stated by the report text or it is absent. The deterministic path no longer defaults a Jakarta-scoped report with no named place to "DKI Jakarta", and it returns a null label. A model's label and approximate coordinate are kept only when the report text states the place: the label, or any comma-separated part of it, must appear in the text (case-insensitive), or the worker can match a gazetteer place named in the text. Otherwise both become null. The point's `geometry_source` is `source_text` only when every claim comes from PetaBencana or BMKG, whose coordinates are parsed from the source's own text. Otherwise it stays `model_approximate`. This supersedes the HOSTED-10 sentence that no source gives a coordinate today. An event with neither a label nor a coordinate is reported as `location_missing` by the ADR-061 gate and waits for a moderator. No geometry row is written, so `source_text` points are still `pending_geometry_writer`. The code is in `apps/worker/src/layers/l2-model-grounding/proposal-engine.ts`, `apps/worker/src/layers/l4-application-integration/public-point.ts` and `apps/intelligence/src/structured-interpretation.ts`.

## Amendment (HOSTED-15, 17 Nov 2026): origin rows for agent-published events

The publication transaction (`publishInTransaction`, `proposal-publication.ts`) now writes one `evidence_origins` row per registered source of a published claim, through `writeOriginRows`. Its id is `origin-` followed by 40 hex characters of SHA-256 over `origin:<dataset_kind>:<source_id>`, so every publication from that source reuses one row. A claim whose source is not in the registry gets no origin, and its `origin_ids` stay empty. The origin's actor label is the registry display name, and `record_json` holds the registry's public hosts only. Its `origin_kind` follows the claim's evidence label (`issuer_notice` as `issuer_statement`, `attributed_report` as `reporter_observation`, `crowdsourced_observation` as itself, anything else `unknown`). Its `lineage_relation` and `independence_status` are `unknown`, because publication proves neither, and multi-source is still not corroboration. Each origin is linked in `origin_evidence` to the persisted evidence the version cites, which is the same support every claim carries. A multi-revision publish has no support, so its origins have no link rows yet, and their `discovery_evidence` minimum of one is not met. Migration 051 grants the publication role INSERT only, on the listed columns of the two tables. The writer uses a bare `ON CONFLICT DO NOTHING`, which needs no read grant, because each table's only unique key is its primary key. The role still cannot read origin rows. No AI call or pipeline step is added, and map points stay skipped (HOSTED-10). This amendment supersedes the origin statement in the HOSTED-10 "still hidden on the DB path" bullet. Whether a given agent event now appears on the public DB list also depends on the strict projector's other target rules, which this amendment does not change and which is not verified end to end here.

## Amendment (HOSTED-18, 17 Nov 2026): whole-view events are listed without a place id

Owner decision (17 Nov 2026): whole-view events are listed without a place id (owner decision 17 Nov 2026); this departs from the domain schema's place requirement, noted, contract not changed.

- A non-group agent event that has a label, no place id and no geometry is listed by the public list with `location_display` "whole_view". Its claims may carry no target as well. Impacts keep the place rule.
- The Event 2.0 record has no label slot, so the publish decision records `location_label_present` in `publication_decisions.record_json`. Migration 052 exposes only that boolean, through `waspada.public_event_location_status`, to the public reader.
- Versions published before migration 052 carry no flag and stay skipped. An event with neither a label nor a place stays refused with `INVALID_EVENT`. Group notices are unchanged, and a whole-view event never gets a map pin.
- The public list response carries `location_display` only on a whole-view event. It is an optional key, already declared optional on `EventView`; the OpenAPI document does not list it (existing gap, not changed here).

## Amendment (HOSTED-22, 17 Nov 2026): public attribution follows source approval at publication

Owner decision (16-17 Nov 2026): approving a source grants public display of its attribution. The publication transaction (`publishInTransaction`, `proposal-publication.ts`) now derives the attribution from the source's approval, through `writeSourceAttributions`. For each supporting evidence reference of a published version, it inserts one `public_attribution_review_decisions` row with `decision_status` "approved" and actor `agent:auto-publisher`, when the reference's source (its revision's `source_id`) is a claim source that passed the public-display rights check and is `approved` in `source_registry`. The public name is the registry display name. The link is the revision's canonical URL, and only https passes, with no credentials and no credential-like query parameter. The publish time is the revision's own `published_at` from the item's pubDate, or NULL. The retrieval time is never used as a publish time (F-14), and `source_observed_at` stays NULL. The writer is insert only, with `review_version` 1 and a bare `ON CONFLICT DO NOTHING`, so a repeat changes nothing and a later moderator decision on the same reference is never overwritten. Migration 053 grants the publication role INSERT on the listed columns, and SELECT on five `report_revisions` columns (`dataset_kind`, `report_revision_id`, `source_id`, `canonical_url`, `published_at`). It grants no read of the attribution table and no permitted text. A source without a row gets no approved attribution, so the projector refuses that version (`ATTRIBUTION_FAILED`). The public list service then skips that one event (its only log line is a count, `public_event_list_skipped`), and the page still renders. The detail service treats a supporting reference with no approved attribution row as missing, so `/api/v1/events/{id}` answers not found, never a server error. Both behaviours fail closed for that event alone. This amendment does not change the publication gate or the rights check.

Owner decision (17 Nov 2026): all 16 live sources are approved with public display. The PetaBencana and BMKG seeds now carry the RSS public-display grant (`reuse_basis` with `public_display`). The hosted bootstrap and the local `serve:live` seed call `upgradeStructuredPublicDisplayGrants`, which changes only a legacy row that is still `approved`, `active` and auto-acquisition enabled, with `reuse_basis` exactly `['public']`. Revoked, disabled and already-changed rows are never touched. The structured inserts (`index.ts`, `tools/serve-live-pipeline.ts`) store `report_revisions.published_at` from the feed's own time (PetaBencana `created_at`, BMKG `DateTime`) when it is a valid instant, else NULL. A value equal to `retrieved_at` (the BMKG in-memory fallback) is never stored (F-14). Revisions stored before this change keep NULL, and nothing is backfilled.

The gated RSS path (`persistAcceptedRssItem`) now writes `report_revisions.published_at` from pubDate, and the intelligence job runner passes the revision's `published_at` (or null) to the interpreter instead of `retrieved_at`.
